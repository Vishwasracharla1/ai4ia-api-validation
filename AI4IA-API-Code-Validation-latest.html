1 — Summary

1.1 Opinion

The backend is validated here against published external standards only. On that basis it is not production-ready, and the reasons are concentrated rather than diffuse.

Data is reachable by the wrong people. The archive and dashboard answer anonymous callers on the running deployment; insights have no owner, so every signed-in user reads every other user's research; the concept mindmap will load another user's storyline and hand back their prompt. Video jobs and media, by contrast, check ownership on every route — the pattern exists and needs extending.

The credential system is well built and badly configured. Argon2id, hashed rotating refresh tokens and constant-time OTP checks meet the standard, but access tokens live for weeks and cannot be revoked, password-reset codes can be requested and guessed without limit, and a missing signing key or API key silently disables protection instead of stopping the service.

The quota is a policy, not yet a guarantee. The 1-running/3-queued job limit is enforced by a read-then-insert that concurrent submissions pass together, is computed by scanning every job on the platform on each submission, and a failed dispatch leaves a phantom queued job that counts against the user; rejections give clients no Retry-After, and model-backed endpoints have per-minute limits but no daily cost budget.

Nothing gates a release. Over 1,400 tests exist, but CI runs none of them, scans no dependencies and resolves unpinned packages at build time.

Set against this, much of the code meets the standard (section 6) — most remediation is extending patterns that already exist in the codebase rather than inventing new ones.

2.3 API findings in detail

A-01CriticalAPIArchive DashboardLIVEBusiness data is served to anonymous callers
OWASP API2:2023 · CWE-306 Missing Authentication for Critical Function
Observed

An anonymous GET /api/archive/speakers (no Authorization, no X-API-Key) returned 200 with 43,552 bytes of archive data. The archive and dashboard routers carry only the shared-key dependency and never resolve a user, and that dependency returns early when API_KEY is empty — so the deployment serves search, speaker, fragment and source-video routes to the internet.

Evidence

backend/app/main.py:440 · backend/app/core/auth.py:16 · backend/app/core/settings.py:22

Impact

The full speaker archive, fragment text, semantic search and source-video streaming are public on the deployment; embedding and translation cost is spent on behalf of anyone.

Remediation

Add Depends(get_current_user) to the archive and dashboard routers and treat the API key as an additional control, not the only one; refuse to start in production when API_KEY is empty.

A-02HighAPIAll routersLIVESecured operations document no authentication or authorization failures
OpenAPI 3.x responses · RFC 9110 §15.5.2 / §15.5.4
Observed

93 of 102 operations declare a security requirement, but 0 declare 401 and 0 declare 403; 93 secured operations list neither. 0 declare 404, 0 409, 0 429. The only error code documented at scale is FastAPI's automatic 422 (87/102).

Evidence

GET /api/models/status · GET /api/auth/me · PATCH /api/auth/me · POST /api/auth/me/password/request-otp

Impact

Generated clients have no typed path for 401/403/404/409/429; negative-path contract testing is impossible.

Remediation

Declare 401, 403, 404, 409 and 429 per operation through responses= (a shared dict per router) with one error schema.

A-03HighAPIAuth All routersLIVE401 responses omit the WWW-Authenticate challenge
RFC 9110 §11.6.1 · RFC 6750 §3
Observed

GET /api/video-jobs → 401 {"detail":"Not authenticated"} with no challenge header. GET /api/video-jobs → 401 {"detail":"Invalid access token"} with no challenge header. RFC 9110 requires every 401 to carry at least one challenge.

Evidence

backend/app/core/auth.py:35

Impact

Standards-compliant clients cannot discover the scheme; conformance tooling fails every denial.

Remediation

Return WWW-Authenticate: Bearer realm="ai4ia" (with error="invalid_token" on expiry) from get_current_user.

A-04MediumAPIAll routersLIVEA missing API key is answered 403, not 401
RFC 9110 §15.5.2 · §15.5.4
Observed

A missing or wrong API key raises 403 Forbidden; a missing credential is 401 territory (RFC 9110 §15.5.2 vs §15.5.4). Live: a random X-API-Key on /api/archive/speakers returned 200 — the key is not enforced on this deployment at all.

Evidence

backend/app/core/auth.py:15

Impact

A-05HighAPIAll routersLIVEErrors are untyped and use incompatible shapes; no RFC 9457 problem details
RFC 9457 · OpenAPI response schemas
Observed

Error bodies observed live: {detail:"…"} (GET /api/video-jobs 401); text/plain text (OPTIONS /api/health 400). C-04HighCodeAuthLIVEAccess tokens cannot be revoked and live for weeks
CWE-613 Insufficient Session Expiration · OWASP API2:2023
Observed

Access tokens live 30 days (measured from a live token's exp − iat). The JWT carries only sub, persona, iss, iat, exp — no jti or token version — and get_current_user trusts the persona claim without a database read. Demotion, deactivation, password reset and logout revoke refresh tokens only; the access token stays valid until it expires.

Evidence

backend/app/core/security.py:129 · backend/app/core/auth.py:44 · .env:7

Impact

A demoted admin keeps admin rights, and a stolen or deactivated user's token keeps working, until expiry.

Remediation

Return the TTL to ≤15 minutes (the refresh flow already exists), add a token_version claim checked against the user row, and bump it on persona change, deactivation, password change and logout-all.

6 — Practices that meet the standard

Recorded so that remediation propagates what already works. Each practice is re-checked on every run.

Credentials

  • Passwords hashed with Argon2id (time 3, memory 64 MiB, parallelism 2 — above the OWASP minimum); legacy plaintext rows compared in constant time and upgraded on first login.
  • Refresh tokens are 384-bit random values stored only as SHA-256 hashes, rotated on every use, with family revocation on reuse.
  • One-time codes come from secrets.randbelow, are stored hashed, verified with hmac.compare_digest, expire in 10 minutes and allow five attempts.
  • JWT verification pins the algorithm list and checks the issuer — no alg=none or algorithm-confusion path; user_id always comes from the verified token.
  • Refresh cookie is HttpOnly, Secure by default and path-scoped to /api/auth.

Authorization

  • Every video-job and media route resolves the job and calls _assert_owns, answering 404 rather than 403 so job existence is not disclosed; the job list is filtered by owner.
  • Admin, ingest and provenance routers require the admin role at router level; admin cannot be self-assigned at signup or through the persona upgrade.

Input handling

  • Media is served through a registry and _safe_path (resolve() then relative_to the allowed roots); HLS segment names and subtitle formats are allow-listed.
  • No shell=True, eval, pickle, yaml.load or verify=False; subprocesses take argv lists; every outbound HTTP call sets a timeout.
  • List endpoints bound their page size in the contract (le= on every declared limit) and request bodies bound prompt length and duration.

Resilience

  • A Redis-backed limiter shared across replicas protects login, OTP resend, job creation and the model-backed endpoints; ingest allows one sync at a time and answers 409 otherwise.
  • Generic handlers keep stack traces and pydantic internals out of 500/422 bodies.
  • Schema DDL is serialised with a Postgres advisory lock; job progress uses an atomic partial-update function.

HTTP semantics

  • Wrong-method requests return 405 with an Allow header; unknown routes return JSON 404; CORS preflights from unlisted origins are refused.

7.1 Method and confidence

The published contract was retrieved from the running service and measured operation by operation against OpenAPI 3.x structural rules and HTTP semantics, then reconciled with the router tables in source. Runtime behaviour was established with read-only probes: anonymous and authenticated reads, wrong-method, unknown-route and malformed-payload requests, CORS preflights, header inspection, and short throttle series against a random identity that cannot exist (so no mail is sent and no real account is affected). Static rules were evaluated over the source tree, configuration, Dockerfile and CI workflow. No job was created, nothing was written, no schema was changed and no attempt was made to bypass a control.

7.2 Limits of this validation

The deployment exposes no build identifier, so equivalence between the reviewed source and the running service is inferred from matching routes and behaviour. Object-level authorization, the quota race, idempotency and concurrency control are reported from source, because confirming them needs writes or a second user's data. Dependency vulnerabilities are not enumerated — no scanner runs in this pipeline (C-10), and this validator deliberately adds none. Logging in as the configured account triggers the model warm-up, as any login does.
